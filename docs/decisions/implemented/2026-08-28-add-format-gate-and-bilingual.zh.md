# 补上格式校验脚本，并保留中英双语三元组

## 决定了什么

推翻 [2026-08-28-decision-record-lifecycle](./2026-08-28-decision-record-lifecycle.zh.md) 里"暂不做双语、暂不上脚本"这两点：

1. `implemented/` 和 `archived/` 下的每条记录必须同时存在 `.zh.md` 和 `.en.md` 两个文件（`proposed/` 阶段允许只写一种语言，降低探索期的摩擦）。
2. 新增 `scripts/verify-decision-records.mjs`，检查文件名格式、必需章节、双语配对、以及归档记录是否被改动。接入方式为 `npm run decisions:check`，经 lint-staged（husky pre-commit）在提交时强制跑；`verify` 链和 CI 里也各有一道。

## 背景

习惯还没养成的阶段，光靠自觉容易第一周就走形——这正是原始报告"哪些不要照抄"里反复强调的"先做零成本的，再碰门禁"的反面情况：如果规则从第一天就不执行，团队会很快学会绕过它，而不是养成习惯。同时希望尽量保留 DSH 原始机制的完整设计意图，包括"翻译也是被冻结内容的一部分"这一条，而不是为了省事简化掉。

## 考虑过的替代方案

- **继续先跑一段时间再决定要不要脚本** — 报告建议的顺序是"先零成本，再碰门禁"，但这条建议假设的是团队已经有一定自觉性；对刚起步、只有一两个人在维护的约定来说，"没有强制"等于"很快就没人管"，收益不一定适用于当前场景。
- **只加脚本，不加双语** — 双语三元组本身没有格式风险，加不加不影响脚本设计；但用户明确要求保留，说明双语被当作对原始机制的完整性要求，而不是可选项。
- **双语从 `proposed` 阶段就强制要求** — 会提高"随手写一条草稿"的门槛，探索阶段允许先用一种语言把想法定下来，等确定要落地（进入 `implemented`）才要求配齐两种语言。

## 为什么这样选

强制执行的成本很低（一个几十行的 Node 脚本 + 一个 git hook），但能立刻防止文档从第一天就开始走形；双语要求虽然让每条 implemented/archived 记录的写作成本翻倍，但用户明确认为这是值得保留的完整性，而不是可以为了省事牺牲的部分。`proposed` 阶段保持单语，是为了不让"记录一个还没定下来的想法"这件事变得太重。
