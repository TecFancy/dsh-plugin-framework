# 落地验证纪律与破例签名（克制工程 A 档三条）

## 决定了什么

把克制工程分析（见 `docs/restraint-engineering-report.md`）评出的三条 A 档规则，以「软规则 + review 强制」的形态写进 AGENTS.md 和插件开发 skill，不新增机械门禁：

1. 只报告实际运行过的命令；被权限/环境挡住时先原样重试，再谈改代码（报告 N3/N4）。
2. 测试描述行为，不描述正确性；有意的行为变更在同一次改动里更新测试，并在 PR 里说明理由（N5）。
3. 破例必须就地签名：`eslint-disable`、覆盖率豁免、被跳过的测试都要带理由；review 检查理由是否成立（「可见的例外」元模式）。

## 背景

restraint 报告把这三条排在「阶段一」：零成本、立刻改变 agent 行为。本仓库 `src/` 当前有 0 个 `eslint-disable`、0 个被跳过的测试、0 个 TODO/FIXME——现在上机械门禁没有猎物可挡，而报告自己说过「一道从来没挡住过任何人的门禁，等于不存在」。这个仓库是模板块：AGENTS.md 和 skill 里的规则会随模板复制到每个下游插件，所以软规则要在第一个真实破例出现之前就位。仓库同时面向多个 agent（Claude Code / dsh / Codex）开放，而真机验证（装进真实 profile 冒烟、浏览器 UI、远程 RPC）不在任何门禁覆盖范围内——这正是验证幻觉最容易发生的地方。70% 覆盖率门槛还制造了「为凑覆盖率改弱断言」的反向激励，而模板测试会把这种习惯传给照着抄的下游插件。

## 考虑过的替代方案

- **立即上机械门禁（覆盖率豁免清单、eslint-disable 理由检查）** —— dsh 的做法；但当前代码树里一个破例都没有，门禁挡不到任何人，而报告警告过「永不触发的门禁只是仪式」。推迟到第一个真实破例或下游插件反馈出现后再做。
- **全量照抄 dsh 的 N1-N5** —— N1（注释视角泄漏）、N2（防御性膨胀）及其配套工具真实存在，但本仓库还小且年轻；报告自己把这三条排在最先，其余等仓库长大或出现真实事故后再补。
- **什么都不做** —— 代码树今天确实干净，但「今天干净」正是立规矩的时机；规则的作用是在第一个破例和第一次真实环境阻塞出现时，让仓库保持干净。
- **AGENTS.md + skill 软规则（选定）** —— 零成本，随模板传播，通过现有的「Relies on humans」表和 skill 的验证章节由 review 强制执行。

## 为什么这样选

这三条是「行为塑造」而非「门禁塑形」：验证声明活在门禁之外，断言意图活在 PR 讨论里，两者都无法机械化。选择的形态遵循报告自己的路线（「先做零成本的，再碰门禁」）和它的元模式——带强制就地理由的软规则，比会被绕过的硬规则更管得住人。模板传播效应让这个时点是本仓库生命周期里立规矩最便宜的时刻。
