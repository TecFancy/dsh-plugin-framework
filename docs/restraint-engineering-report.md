# 克制工程

**案例研究 · DeepSeek Harness (`D:/source/dsh`) 代码库分析**

> AI 驱动的 vibe coding 会像人类项目一样腐化，往往腐化得更快，因为落笔的人从不为下一次改动负责；还有几类腐化是它独有的，人类代码库几乎不产生。这份报告拆解了一个把这两件事都管住的开源代码库，并给出可以直接搬进 RSP 项目的分阶段方案。

来源：Claude 生成的报告（同一分析主题的扩展/RSP 定制版），存档自 <https://claude.ai/code/artifact/78a1afbc-0522-4d0d-8040-507b81d89292>（2026-08-28）。与更早的短版笔记 [restraint-engineering.md](./restraint-engineering.md) 是同一次代码库分析，这一版补充了诊断框架、AI 特有腐化的完整分类、以及针对 RSP（C# / ASP.NET Core / Azure Functions + React / TypeScript）的落地映射表和分阶段路线。

**关键数字**：45,673 个符号节点 / 99,626 条调用边 · 55 个能力包组，数百个独立小包 · 561 / 144 条已实现决策记录 / 已冻结归档 · 15 个按场景命名的门禁集合 · 227 个包级运行时不变量断言。

## 论点

这套代码库不靠"写得更规范"来对抗熵增，靠的是三件具体的事：**把决策的理由变成一份有生命周期、会被冻结的记录，而不是一次性的文档**；**把"删除、收敛、归档"做成和"新增功能"同等重要、同样被计入交付的常规动作**；以及**允许一切破例，但要求每一次破例都留下署名和理由**。下面先说问题，再拆机制，然后单独讲一类只有 AI 才会大量产生的腐化，最后给落地路线。

## 01 / 诊断：vibe coding 为什么会比人类项目烂得更快

人类写烂代码，是因为懒、因为没时间、因为记不住上下文。AI 写烂代码，是同一套原因加了速：它从不觉得累，永远"有时间"，而且每次对话都从零开始猜你的意图。

- **理由不落地。** 代码留下了，但"为什么这么写、放弃了哪个方案"没有留下。下一个 agent（或下一个人）只能重新猜，猜错了就再造一个类似但不一致的抽象，同一个问题被解决三次，每次都不一样。
- **规则不可执行。** 约定写在 CLAUDE.md / 团队 Wiki 里，agent 读得到，但读到不等于会遵守。没有一道机械门禁会在提交时真的挡住违规，规则就会慢慢变成"建议"，最后变成没人记得的历史。
- **只有增长，没有收敛。** 每次对话都在"加东西"里被奖励：新功能、新分支、新兼容层。没有对称的动作去做"删东西"并把它算作一次正经的交付，代码量只会单调上升。
- **边界靠自觉。** 模块边界如果只写在文档里，会被"看起来很合理"的一行 AI 生成代码一点点磨平，直到某天发现所有东西都能直接调用所有东西，谁都不敢再重构。

## 02 / 解剖：DSH 具体做了什么

五个机制，每一个都对应上面某个病灶。全部有代码和数据支撑，不是读文档得出的印象。

### M1 · 决策记录是有生命周期的，不是一次性文档

`.agents/notes/`

每条 Agent Note 的路径本身就编码了状态：`{proposed|implemented|rejected|archived}/{分类}/日期-主题.md`。"已实现"的记录要求正文用现在时描述"决定了什么"、必须包含"考虑过哪些替代方案及为何放弃"，并随代码演进保持事实同步；不允许把决定本身悄悄改成另一个决定，只能新开一条并互相链接。

生命周期：`proposed → implemented → archived（哈希封存，永不再改）`，或 `proposed → rejected（过时后删除）`。

- 561 implemented · 144 archived · 26 proposed · 11 rejected
- `scripts/verify-agent-note-format.ts` 94 行，格式与生命周期状态的一致性门禁
- `scripts/verify-archived-agent-notes.ts` 115 行，归档三元组的哈希清单只允许追加，不允许改动

最关键的一步：归档判断不靠字数或时间，靠校准过的人类判断。`dsh-archive-agent-notes` 这个 skill 给出了反例：一条 248 词的记录（"事件溯源会话"）因为是基础性权威保留；一条 1,498 词的记录（"Commander 参数适配器"）因为只是实现细节、没有未来指导价值，直接归档。归档后的记录被整体冻结，不能再编辑、翻译、修复链接，只能被新文档引用为历史事实。

> **解决的问题**：理由不落地。把"为什么"从代码作者的脑子里搬到一份会被下一个 agent 强制读到、并且不会腐烂（冻结）也不会无限膨胀（归档收窄）的记录里。

### M2 · 该守的规则，写成门禁脚本，不写成"建议"

`scripts/verify-*.ts`

约定不是靠 agent"读文档时表现好"，而是靠一段能挡住提交的代码。举几个真实存在、真在跑的例子：

- `verify-export-jsdoc.ts` 617 行，用 TypeScript 编译器 API 真的遍历 AST，检查每个导出的函数 / 方法是否有参数与返回值文档；遇到识别不了的语法形态直接判失败（"fail closed"），而不是放行
- `verify-doc-budgets.ts` 58 行，给核心文档定"字数上限清单"，上限只能往下调（留 5% 余量），想往上调必须在 PR 里写理由
- `vitest.config.ts` coverage.thresholds：statements/branches/functions/lines 全部 100，且 `perFile:true`（逐文件而非整体平均）
- `.jscpd.json` `minTokens:60, minLines:6, exitCode:1`，重复代码检测直接让构建失败
- `verify-package-invariants.ts` 检查的是"包之间的关系是否成立"，不是"文件是否存在"这种表面合规
- `knip.json` `--treat-config-hints-as-errors`，连"门禁脚本自己的配置写漂了"都算门禁失败，不允许静默弱化
- `verify-cordis-config.ts` 遍历 TypeScript Project Reference 图，断言每个包只注册进一个编译聚合、插件清单里的依赖必须显式声明——把"架构分层对不对"变成一次图遍历断言，不是代码评审时的印象判断

> **解决的问题**：规则不可执行。人和 agent 都会在"应该做"和"必须做"之间选后者，只要后者真的会挡人。这些脚本把文字规则变成了退出码。

### M3 · CI 不是"一键跑全部"，是按场景拼装的门禁图

`scripts/run-gates.ts`

一份 968 行的调度器，定义了 15 个命名场景（`ci-primary / ci-coverage / ci-snapshot / hygiene / doc-sync / check-all …`），每个场景是一张显式的依赖图，还带并发上限（避免本地机器被同时跑的 4 个 TypeScript 编译进程拖死）。配套的口径写得很直白：**提交或推送前不默认跑全套**，只选覆盖了这次改动面的最小证据集，全量覆盖是 CI 的事，不是每次本地检查的事。

18 个独立的 GitHub Actions workflow 文件，职责很窄：`issue-policy.yml`、`expected-filenames.yml`、`e2e.yml`、`docs-pages.yml` ……没有一个"什么都干"的巨石 workflow。

> **解决的问题**：门禁一旦又慢又笨重，人和 agent 都会想办法绕过去（`--no-verify`、跳过 hook）。把门禁拆细、按场景选，才能长期被真的执行，而不是被抄近路。

### M4 · 架构按"能力接缝"切成小包，不许长成巨石

`packages/`

55 个包组，每个能力（shell、fs、web、subagent…）都显式拆成三个角色：接口定义（Service Definition）、实现（Provider）、消费方（Consumer），这三个角色被当作一等概念写进规范，不是自然长出来的分层。图谱分析显示包与包之间的高扇入节点（`core`、`typert`、`util`）本身就是被设计成"只被依赖、不反向依赖"的核心层，边界在结构上可验证，不只靠自觉。

> **解决的问题**：边界靠自觉。把"这次改动该不该跨包直接调用"这个判断，从每个开发者/agent 的经验，变成"包的物理位置和依赖方向摆在那里，越界会被图谱和门禁看见"。

### M5 · 收敛是提交历史里能查到的真实动作，不是口号

`git log`

最近 1,000 条提交里，约 2.8% 的标题直接包含 simplify / remove / prune / duplicate / archive / consolidate 这类词。真实样本：`cc25bceec8` "simplify terminal contribution branch"，一个文件，+5/-7 行，净删除。commit 前缀本身就带了 `refactor`、`cleanup` 这类"收敛型"分类，和 `feat`、`fix` 平级，不是事后才想起来贴的标签。更进一步，归档/简化被做成了一个常设的、反复执行的 skill（`dsh-archive-agent-notes`、`dsh-find-simplifications`），而不是"年底大扫除"式的一次性活动。

- 门禁不只挡新代码，也挡门禁作者自己的后续提交：`5d9f026e55` "fix(settings): correct the exposure analysis and satisfy the coverage and lint gates"、`13152903c7` "fix(subprocess): satisfy the oxlint gates in the Windows inspector"，这是这个仓库里一类固定的 commit，专门用来"让代码通过别人刚加的检查"
- 撤销同样是一等公民，不是静默 force-push：`7ce85283b5` Revert PR #2608，随后走一条独立的重新落地 PR，revert 本身留痕、可追溯

> **解决的问题**：只有增长，没有收敛。让"删代码、删文档、归档决定"和"加功能"一样，是一种被命名、被反复执行、能在 git log 里被看到的日常动作。

## 03 / 新病种：只有 AI 才会大量产生的腐化

前面两节的病灶，人类项目也有，AI 只是加速了它们。这一节不一样：下面五种腐化，人类代码库几乎不产生，是 vibe coding 独有的。这也是这个仓库里投入最"反常"的一部分，而且恰好是最便宜、最该先抄的一部分。

### N1 · 推理过程泄漏：注释的视角停留在"那次对话"

`dsh-trim-cot-leakage`

AI 写注释和文档时，视角常常是"我这次会话"，不是"这个仓库"。于是它写下只有当次对话能看到的引用（`(decision 7)`、`plan §1.4`、`audit C2`）、叙述变化而不是状态（"以前是…现在不再…"）、对着一个已经离开的评审者辩解（"这个转换是安全的，因为它只是…"）、或者复述控制流（"我们先 X，然后 Y"）。这些文字在写下的当天读起来都通顺，三个月后全部变成噪音，因为它们引用的东西根本不在仓库里。

DSH 把这件事做成了一个有 8 类分类法的专门技能，并且给了一句话判据：

> 一个只能看到当前代码、没有任何会话记录 / PR 讨论 / 未提交草稿的读者，能不能**解析每一处引用、验证每一条断言**？不能，就把还活着的事实用仓库的视角重写，其余删掉。

8 类分类法：死引用 · PR/栈视角 · 变化叙述 · 评审编排 · 对评审者的辩解 · 复述与推导 · 含糊的计划残留 · 工作语言残留。配套一份对称的"什么不算泄漏"清单，防止清理过头。

关键的一半其实是那份反向清单：`#1470` 这类 issue 引用、`oxlint-disable ... -- reason` 的抑制理由、"没有 X 就会 Y"这种反事实回归说明、"（实测：512 层嵌套≈0.15s）"里的实测出处，都**必须保留**。清理规则自己带了护栏，甚至明确列出四种"改过头"的失败形态：把义务写成背书、把设想写成已实现、删掉真事实、丢掉出处。

> **解决的问题**：AI 生成的散文会以"当次会话"为视角沉淀，形成一种人类项目很少见的文档腐化。企业里最直接的落地是给 code review 加一条判据，成本几乎为零。

### 另外四种（简述）

- **N2 · 防御性代码膨胀。** AI 的默认习惯是到处加空值检查、到处包 try-catch、到处做运行时校验。DSH 反过来立规矩：**在类型系统已经保证的同进程边界上，禁止再加运行时校验、兜底分支和敌意输入测试**，同时把真正需要校验的边界一个个列清楚（解析与配置、队列、模型与工具的 JSON、持久化文件、worker、进程、wire）。清单之外，相信类型。
- **N3 · 环境错误误诊。** agent 被沙箱挡住（凭证、网络、文件监听、IPC）时，最糟的反应是把它当成代码 bug，然后开始"修"本来正确的逻辑。规则是：**先用最小权限升级原样重试**，拿到沙箱证据再谈诊断，并且永不借此绕过真实的测试失败或被测的产品沙箱。
- **N4 · 验证幻觉。** "**只报告实际运行过的命令**"。这一条专门防 agent 声称"测试都过了"。配套的是"证据要匹配改动面"：行为改动跑聚焦测试，模型或用户可见输出跑快照，文档改动跑 doc-sync，发布路径跑构建与 hygiene，而不是笼统地说一句"已验证"。
- **N5 · 测试固化过时行为。** "**测试描述行为，不描述正确性**。行为过时了就连测试一起改，并在 PR 里解释为什么。"没有这条，AI 会把既有测试当成不可动摇的真理，于是过时行为被永久钉死在测试里，重构成本一路上升，最后没人敢动。

## 04 / 元模式：可见的例外

如果只能从这个仓库带走一条设计原则，是这条。它在六个互不相关的机制里反复出现，而且和技术栈完全无关。

几乎每一道门禁都留了逃生口，但**没有一个逃生口是隐形的**。每一次"我这里就是要破例"都必须变成一份署名、带理由、会出现在 diff 里、能被评审的产物：

- 包没有可断言的运行时不变量 → 必须在代码里写 `No runtime invariant: <本包特有的理由>`，空着或写套话直接失败（227 个 invariant 文件）
- 包 README 没有"已知限制" → 必须在 `verify-package-readme-limitations.ts`（93 行）的白名单里留一条带理由的条目
- 重复代码确实无法避免 → 用 `/* jscpd:ignore-start */` 就地标注，而不是往全局 exclude 里塞路径
- 导出成员确实不需要文档 → 只能落在脚本里那份枚举好的豁免清单，不能临时放行
- 文档字数上限确实需要放宽 → 只能在 PR 里写明理由后上调，平时只允许往下调
- lint 抑制、覆盖率忽略、空 catch → 理由是**必需的散文**；理由写错了要改对，不许删掉

> 规则本身是软的（都能破例），硬的是**"破例必须留下署名和理由"**。这比"禁止破例"更可执行：前者会被绕过去，后者只会留下一条可以被讨论的记录。

企业落地成本极低，且不依赖任何具体技术栈：把所有 `#pragma warning disable`、`SuppressMessage`、`eslint-disable`、被 Skip 的测试，一律要求带一句"为什么"，并在 review 里把"这个理由是否成立"当成正式检查项，而不是扫一眼放过。

## 05 / 零碎：另外六个便宜的机制

都是小东西，实施成本很低，但每一个都堵住了一类具体的漂移。

| 机制                   | 做法                                                                                                                                                         | 堵住的漏                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 规则自带失效条件       | 根规范里有一节明确写着"在第一个正式版本发布时删除本节"。规范文件还按目录分层（根 / packages / examples），每层只管自己那层的规则，且规范自己也受字数上限约束 | 临时规则变成没人敢删的历史；AI 指令文件无限膨胀直到没人（和没模型）真的读完 |
| 事故 → 规则双向链接    | 4 篇 postmortem，且 packages 规范里有两条规则直接链回同一篇事故报告                                                                                          | 凭想象写"预防性"规范，规则越堆越多却没有一条来自真实翻过的车                |
| 文档与代码的漂移门禁   | 文档里粘贴的类型声明用 ` ```ts type-equiv ` 围栏 + manifest 注册，`verify-type-equiv.ts` 保证它和源码不漂移                                                  | 文档里的代码示例悄悄和真实签名脱节，读者照着写却编译不过                    |
| 不变量或解释，二选一   | 227 个 `invariant.ts`。要求断言的是"事件流或可变数据之间的真实关系"，不是"服务存不存在"这种同义反复                                                          | 模块没有任何可机械验证的真相，只能靠人读代码判断它有没有坏                  |
| TODO 分级有语义        | `FIXME` 阻塞发布 / `TODO` 尽快修 / `XXX` 也许永远不修。三个词各有明确的承诺级别                                                                              | 所有待办都是同一个 TODO，扫一眼分不出发布阻塞和随手记，于是全部一起烂掉     |
| 流程本身是可调用的产物 | 11 个 skill：预推送检查怎么选最小证据集、code review 看什么、怎么找简化点、怎么归档记录。流程是版本化、可调用的文件                                          | 流程写在 Confluence 上没人点开，更没法被 agent 读到和执行                   |

## 06 / 映射：搬到 RSP 该换成什么

RSP 是 C# / ASP.NET Core / Azure Functions 后端加 React / TypeScript 前端，不能照抄 DSH 的 TypeScript 专用脚本，但每一条机制都有对应的落地方式。

| DSH 机制                | RSP 对应方案                                                                                                                                                      | 落地成本 |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| Agent Notes 生命周期    | 轻量版"决策记录"：去掉中英双语三元组，只留 `proposed / implemented / archived` 三态 Markdown，先从 PR 模板里加一条"是否需要决策记录"的 checkbox 开始              | 低       |
| verify-export-jsdoc     | C# 端开 `GenerateDocumentationFile` 并把 CS1591 提升为 error；TS 端写一条 ts-morph / ESLint 自定义规则检查导出成员的 JSDoc                                        | 中       |
| verify-doc-budgets      | 几十行 Node/PowerShell 脚本 + 一份 JSON 字数上限清单，先挑 3~5 篇最容易膨胀的核心规范文档试点，不要一次铺开全部文档                                               | 低       |
| 100% 逐文件覆盖率       | 不建议照搬满值；改成"新增/变更文件"的差异覆盖率（diff coverage）高阈值，避免历史包袱直接拖垮门禁                                                                  | 中       |
| jscpd 重复检测          | TS 侧直接接 jscpd；C# 侧用 JetBrains dupFinder CLI 或 SonarQube 的 CPD 引擎，先只报告不拦截，观察一个迭代再转成硬门禁                                             | 中       |
| run-gates.ts 按场景拼装 | 用 CI 的 path filter + 可复用 job 模板，明确区分"本地 pre-push 最小集"与"CI 完整集"，本地永远不跑全套                                                             | 中       |
| 能力接缝式小包架构      | 在现有 rsp-backend / rsp-frontend 规范上加一条检查清单：新功能落地前先问"这该不该是一个新的接口 + 实现 + 消费方，而不是塞进现有 Service"                          | 高       |
| 常设收敛 skill          | 每个 sprint 收尾安排一次"简化审查"，把"删除的代码行数 / 归档的记录数"写进 sprint 交付物，而不是只统计新增                                                         | 低       |
| 可见的例外（元模式）    | 所有 `#pragma warning disable` / `SuppressMessage` / `eslint-disable` / 被 Skip 的测试必须带一句理由，review 把"理由是否成立"当正式检查项                         | 低       |
| 推理过程泄漏判据        | code review 加一条判据："这段注释和文档，一个只看当前代码的人能不能全部解析"，顺带把它写进团队的 AI 协作规范                                                      | 低       |
| 只报告实际运行的命令    | 写进 AI 协作规范，并要求 PR 里贴出实际执行的命令与输出，而不是一句"已验证"                                                                                        | 低       |
| 禁止过度防御            | 在 rsp-backend 规范里明确列出"必须做运行时校验"的边界清单（入参 DTO、外部 API、DB 读出、消息队列、配置），清单外相信类型系统；配 Roslyn 分析器管住到处 null-check | 中       |
| 事故 → 规则双向链接     | 每次线上事故产出一条规范条目，条目里链回事故报告；反过来不写没有事故支撑的"预防性"规范                                                                            | 低       |
| 规则自带失效条件        | 临时规范、兼容层、feature flag 一律写明删除触发条件（哪个版本发布后、哪个迁移完成后），到期由 sprint 简化审查兜底清理                                             | 低       |
| TODO 三级语义           | 统一 `FIXME / TODO / XXX` 的承诺级别，并在发布检查里硬卡 `FIXME` 数量                                                                                             | 低       |
| 流程即产物              | 把 code review checklist、发布检查清单从 Confluence 搬进仓库，写成 agent 可调用的 skill / prompt 文件，随代码一起版本化和评审                                     | 中       |

## 07 / 路线：分阶段落地

别一次性搬全套，DSH 自己也是逐条 Agent Note 长出来的。建议按下面的顺序试点。

### 阶段一：基线可见度（一个迭代内）

- 提交信息统一前缀，明确加入 `refactor / cleanup` 这类收敛型分类，与 `feat / fix` 平级
- PR 模板加两项 checkbox："是否需要一条决策记录"、"这次改动删除了什么"
- 挑 1~2 篇最容易膨胀的核心规范文档，先手工定一次字数上限，不用脚本也行
- **所有 lint 抑制、被 Skip 的测试、空 catch 一律要求带一句理由**，这是本报告里性价比最高的一条，今天就能做
- code review 加一条"推理过程泄漏"判据，并写进团队 AI 协作规范
- 统一 `FIXME / TODO / XXX` 三级语义，明确只有 `FIXME` 阻塞发布
- AI 协作规范里写死两条：**只报告实际运行过的命令**；被环境或权限挡住时先原样重试并升级权限，不要改代码

### 阶段二：机械门禁（2~4 周）

- 接入差异覆盖率阈值，只卡新增/变更文件
- 接入重复代码检测，先报告不拦截
- 接入导出成员文档缺失检测，先 warning 不 fail
- 明确列出"必须做运行时校验"的边界清单，清单之外禁止防御性兜底
- 把 code review checklist 从 Confluence 搬进仓库，变成 agent 能读到的文件

### 阶段三：决策日志（1~2 个月）

- 落地三态决策记录文件夹结构 + 一份最小格式校验脚本
- 把"是否需要决策记录"从 checkbox 升级为 code review 的硬性检查项
- 写一份"何时归档、何时删除"的校准示例（参考 DSH 的 calibrated examples 做法），而不是靠字数或时间自动判断
- 建立"事故 → 规则"的双向链接习惯：每条新规范都要能指回一次真实事故
- 给所有临时规范、兼容层、feature flag 补上删除触发条件

### 阶段四：常态化收敛（持续）

- 每个 sprint 或每月固定一次"简化审查"，产出可量化的删除/归档记录
- 把差异覆盖率、重复检测门禁从 warning 转正为真正拦截提交
- 按变更面拆分门禁场景，而不是让 CI 越跑越全、越跑越慢

## 08 / 提醒：哪些不要照抄

- **不要机械照抄 100% 覆盖率这个数字。** 抄的是"用可执行阈值代替道德说教"这个思路，数字要按团队现状重新校准，尤其是有大量历史代码的项目。
- **归档判断不能自动化成字数或时间规则。** DSH 明确禁止用这两者当归档标准，靠的是校准过的人类判断，照搬自动规则大概率会砍掉真正有价值的记录。
- **决策记录系统如果没人真正维护生命周期迁移，会变成第二个文档坑。** 先在一个团队/一类变更上小范围试点，观察是否真的被更新和归档，再决定要不要推广。
- **小包架构的收益来自"接缝显式化"，不是"包越多越好"。** 过度拆分同样是一种熵增，只是换了个碎片化的形式，拆分前要能说清楚这一刀切在哪个真实的能力边界上。
- **清理规则必须自带防过度清理的护栏。** DSH 的推理泄漏清理技能里，"什么不算泄漏"的篇幅和"什么算"几乎一样长，还专门列了四种改过头的形态。只给 AI 一句"删掉冗余注释"，它会连带删掉抑制理由、实测数据和回归说明，那是净损失。
- **门禁没覆盖到的地方要写下来。** DSH 明确记录了自己的盲区（比如两个 SDK 的预期输出必须同一个 PR 一起更新，而主测试套件两个都不覆盖）。承认"这里靠人"，比假装全自动更安全。
- **先做零成本的那几条，再碰门禁。** "抑制必须带理由""只报告实际跑过的命令""TODO 分级"这三条今天就能落地、不需要任何工具，而且立刻能改变 agent 的行为。反过来，先上覆盖率和重复检测门禁，很容易在第一周就被团队集体绕过。
