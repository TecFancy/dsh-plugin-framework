# 克制工程

> 我读了一个用 AI 高强度开发、但没有烂掉的仓库。它靠的不是"写得更规范"，而是几件很具体、很便宜的事。

分析对象：DeepSeek Harness（`D:/source/dsh`，master 分支 `b150a551`）。约 4.6 万个符号、数百个小包、1.3 万次提交。下面的数字都是当时快照。

来源：Claude 生成的文章 <https://claude.ai/code/artifact/1686c7d3-b645-40c5-bf8a-185446fa897d>（2026-08-28 存档）。

## 引子

你提的那个感觉是对的：AI 写代码这件事，时间一长会和人类项目一样开始腐化，而且通常更快。我把这个仓库翻了一遍，包括提交历史、门禁脚本和它自己的规范文档，想看看它凭什么没长歪。

结论比我预期的要朴素。它没有什么特别聪明的架构技巧，真正起作用的是三件很土的事：**把决定写下来并且让这些记录会过期；把该守的规则做成能让构建失败的代码；允许任何人破例，但破例必须签名。**

## 为什么 AI 写的代码烂得更快

人写出烂代码，通常是因为累了、赶时间、或者记不住三个月前为什么那样写。AI 把后面这条放大到了极致：它永远不累，永远"有时间"，但每次对话都从零开始猜你的意图。

真正要命的不是它水平不够，而是**没有任何一方对"下一次改动"负责**。人类工程师至少知道这坨代码下个月还得自己维护，AI 交付完就走了。于是三件事同时发生：做决定的理由留不下来，下一个 agent 只能重新猜，猜错就再造一个类似但不一致的抽象；写在文档里的约定没有牙齿，读到不等于遵守；每次对话都在"加东西"里被奖励，没有任何对称的力量去删东西。

代码量于是单调上升。这不是水平问题，是激励结构问题。

## 第一件事：决定要写下来，而且这些记录会过期

这个仓库有 `.agents/notes/` 目录，每次非琐碎的改动都要留一条记录，说明决定了什么、考虑过哪些替代方案、为什么放弃。目前有 561 条"已实现"和 144 条"已归档"。

光是"写文档"没什么新鲜的，有意思的是后面两条规矩。

第一，记录的状态编码在文件路径里，会随时间迁移：从"提议"到"已实现"，最后进"已归档"。**一旦归档就整体冻结**，不能再编辑、不能修链接、连翻译都不许动，只能被新文档当作历史事实引用。这条看着教条，但它解决了一个真问题：文档最常见的死法不是没人写，而是被后来的人改得半新半旧，最后没人知道哪句还成立。冻结等于承认"这是当时的决定"，而不是假装它永远正确。

第二，什么时候该归档，**不靠字数也不靠时间**，靠人判断，而且他们把判断标准写成了对照例子。

> **两个真实的归档判断**
>
> 一条 248 词的记录（关于会话事件溯源）被保留，因为它是基础性的权威说明，后来的人还得靠它做判断。
>
> 一条 1498 词的记录（关于某个命令行参数适配器）被直接归档，因为它只是实现细节，对未来的决策没有指导价值。

短的留下，长的归档。判断依据是"未来还需不需要它来做决定"，不是它有多详细。这一点我觉得比整个机制本身更值得抄：任何试图用字数或时间自动判断的规则，都会砍掉真正有价值的东西。

## 第二件事：规则要么能挡住人，要么就别写

这个仓库的约定不靠 agent"读文档时表现良好"，靠的是一段能让构建失败的代码。举三个我觉得最聪明的。

**文档字数上限只能往下调。** 核心文档各有一个字数上限清单，平时只允许收紧，想放宽必须在 PR 里写明理由。这是一个棘轮：文档只能越来越紧凑，膨胀需要付出解释成本。我没在别处见过这个做法，但它精准地治住了 AI 最爱干的事，把一句话的规范扩写成三段。

**覆盖率是逐文件 100%，不是整体平均。** 整体平均可以让一个写得很烂的文件躲在一堆测试充分的文件后面，逐文件就没处躲。更妙的是他们在文档里写明了怎么理解未覆盖的行：**那往往是该删的死代码，不是该补的测试**。同一个数字，换个解读方向，覆盖率就从"补测试的负担"变成了"找死代码的工具"。

**连门禁自己的配置写漂了也算失败。** 死代码检测工具开了"配置提示也当错误"，不允许悄悄弱化规则。

这些是不是真在起作用，看提交历史就知道。这个仓库有一整类 commit，标题就是"让代码通过某个检查"，比如"satisfy the coverage and lint gates"、"satisfy the oxlint gates in the Windows inspector"。也就是说，门禁不只挡新人，也挡门禁作者自己后来的提交。**一道从来没挡住过任何人的门禁，等于不存在。**

还有一点值得学：它的 CI 不是"一键跑全部"。有一个调度器定义了十几个命名场景，提交前只跑覆盖这次改动面的最小集合，全量是 CI 的事。理由写得很直白，门禁一旦又慢又笨重，人和 agent 都会想办法绕过去。

## 第三件事，也是我最想抄的：破例要签名

这条是我读完之后最想立刻用起来的，因为它几乎不花钱，而且跟技术栈完全无关。

这个仓库里几乎每道门禁都留了逃生口，但**没有一个逃生口是隐形的**。每一次"我这儿就是要破例"，都必须变成一份带理由、会出现在 diff 里、能被评审的东西：

- 某个包确实没有可断言的运行时不变量，那就得在代码里写清 `No runtime invariant:` 加上这个包特有的理由。空着不写，或者写句套话，门禁直接失败。这样的文件有 227 个。
- 某个包的 README 确实没有已知限制要声明，那就得在白名单里留一条带理由的条目。"我们没有已知限制"这句话本身需要解释。
- 某处重复代码确实无法避免，那就在那一行就地标注，而不是往全局排除列表里塞路径。
- lint 抑制、覆盖率忽略、空的 catch 块，理由都是必需的散文。而且规矩写得很硬：**理由写错了要改对，不许删掉。**

> 规则本身是软的，任何一条都能破。硬的是"破例必须留下署名和理由"。
>
> 这比"禁止破例"更管得住人。前者会被绕过去，后者只会留下一条能被讨论的记录。

换到我们这边，就是所有 `#pragma warning disable`、`SuppressMessage`、`eslint-disable`、被 Skip 的测试，一律要求带一句为什么，然后在 code review 里把"这个理由站不站得住"当成正式检查项，而不是扫一眼放过。

## 几个只有 AI 会踩的坑

上面那些，人类项目也需要，AI 只是让它们更紧迫。但有一类腐化人类代码库几乎不产生。

最典型的是**注释的视角停在了"那次对话"**。你大概见过这种注释：写的时候特别顺，三个月后完全看不懂。因为它引用的东西根本不在仓库里，比如"（见决策 7）"、"设计稿 §1.4"；或者它在叙述变化而不是状态，"以前是 X，现在不再 X 了"；或者它在跟一个早就离开的评审者辩解，"这个转换是安全的，因为它只是……"。

这个仓库给这件事做了一份专门的清理指南，判据只有一句，我觉得可以直接搬进 code review：

> 一个只能看到当前代码、没有任何对话记录、PR 讨论或未提交草稿的人，能不能解析这段话里每一处引用、验证每一条断言？

不能，就把里面还活着的事实用"仓库的视角"重写，其余删掉。

但真正让我觉得这份指南靠谱的，是它另外一半篇幅在讲**什么不算**：issue 编号、抑制理由、"没有 X 就会 Y"这种反事实说明、"（实测：512 层嵌套约 0.15 秒）"里的实测出处，都必须留着。它甚至列了四种改过头的形态，比如把义务写成背书、把设想写成已实现、删掉真事实、丢掉数据出处。如果你只丢给 AI 一句"删掉冗余注释"，它会顺手把抑制理由和实测数据一起删干净，那是净损失。

另外四个坑比较短，一起说：

- **防御性代码膨胀。** AI 的默认习惯是到处加空值检查、到处包 try-catch。这个仓库反过来立规矩：类型系统已经保证的地方禁止再加运行时校验，同时把真正需要校验的边界一个个列清楚。清单之外，相信类型。
- **把环境问题当成代码问题。** agent 被权限或网络挡住时，最糟的反应是当成 bug，然后开始"修"本来正确的逻辑。规矩是先原样重试、必要时升级权限，拿到证据再谈诊断。
- **声称测试过了。** 规范里就一句："只报告实际运行过的命令。"配套要求是证据得匹配改动面，而不是笼统说一句"已验证"。
- **把过时行为钉死在测试里。** 它明确写了"测试描述行为，不描述正确性"，行为过时就连测试一起改，并在 PR 里解释原因。没有这条许可，AI 会把既有测试当成不可动摇的真理，最后没人敢重构。

## 删东西也得算成绩

最后一件事，可能是最难在公司里推的。

这个仓库最近一千次提交里，大约 2.8% 的标题直接是"简化""删除""收敛""归档"这类词。`refactor` 和 `cleanup` 是和 `feat`、`fix` 平级的提交类型，不是事后补的标签。撤销也是一等公民，会老老实实留一条 revert 记录再走一个重新落地的 PR，而不是偷偷 force push 掉。

更关键的是，"找简化点"和"归档旧记录"被做成了两个常设的、可以反复执行的流程文件，而不是"年底大扫除"式的一次性活动。这就是那个对称的力量：只要删除永远不进交付统计，它就永远不会真的发生。

## 搬到我们这边，先做这三件

别一次性搬全套，这个仓库自己也是一条条长出来的。按判断，下面三件今天就能做，不需要任何工具，而且立刻能改变 agent 的行为：

1. 所有 lint 抑制、被 Skip 的测试、空 catch，一律要求带一句为什么。这是全篇性价比最高的一条。
2. AI 协作规范里写死两条：只报告实际运行过的命令；被权限或环境挡住时先重试，不要改代码。
3. code review 加一条判据：这段注释和文档，一个只看当前代码的人能不能全部读懂。

然后是几周量级的：接入差异覆盖率（只卡新增和变更的文件，别用满值去撞历史包袱）、接入重复代码检测但先只报告不拦截、导出成员缺文档先给 warning。再往后才是决策记录目录和"每条新规范都要能指回一次真实事故"这类需要养成习惯的东西。

| 它的做法             | 我们这边换成                                                     | 成本 |
| -------------------- | ---------------------------------------------------------------- | ---- |
| 破例必须带理由       | 抑制指令、Skip 的测试一律要求写原因，review 检查理由是否成立     | 低   |
| 推理泄漏判据         | 加进 code review 清单和 AI 协作规范                              | 低   |
| 文档字数棘轮         | 挑三五篇最容易膨胀的核心规范定上限，几十行脚本就够               | 低   |
| 逐文件 100% 覆盖     | 改成新增和变更文件的差异覆盖率，别照搬满值                       | 中   |
| 重复代码检测         | 前端直接接 jscpd，C# 用 dupFinder 或 SonarQube，先报告一个迭代   | 中   |
| 导出成员必须有文档   | C# 端把 CS1591 提成 error，前端写一条自定义 lint 规则            | 中   |
| 流程写成可调用的文件 | 把 review 清单、发布检查从 Confluence 搬进仓库，跟代码一起版本化 | 中   |
| 删除也算交付         | 每个 sprint 收尾做一次简化审查，删除行数进交付统计               | 低   |

## 别抄的部分

- **100% 覆盖率这个数字别照搬。** 要抄的是"用可执行阈值代替道德说教"这个思路。数字得按我们的现状重新定，尤其是历史代码多的项目，硬上满值只会让团队集体绕过门禁。
- **归档判断别做成自动规则。** 它明确禁止用字数和时间当标准，靠的是校准过的人的判断。做成自动规则大概率会砍掉最有价值的那些记录。
- **决策记录如果没人真的维护状态迁移，会变成第二个文档坑。** 先在一个团队、一类变更上试点，看它是不是真的被更新和归档，再决定推不推广。
- **小包架构的收益来自"接缝清楚"，不是"包越多越好"。** 过度拆分同样是熵增，只是换成了碎片化的形式。切之前得能说清这一刀切在哪个真实的能力边界上。
- **先做零成本的，再碰门禁。** 上面那三件今天就能做。反过来先上覆盖率和重复检测，很容易第一周就被绕过，然后这件事就再也推不动了。

## 最后

单看每个机制都很小，几十行的脚本、一句写进规范的话、一个目录约定。值钱的地方在于它们都被做成了"会挡住你"的东西，而不是文档里的一句期望。

这也解释了为什么社区里很多项目栽了。不是他们不知道该怎么写代码，是他们把这些东西写成了建议。人和 AI 在"应该做"和"必须做"之间，都会选后者，只要后者真的会挡人。
